# Comment and documentation audit

This audit identifies the edits needed to make bcordes comments concise and its implementation documentation accurate and easy to find. It supports [Audit comment and documentation cleanup coverage](https://github.com/bc-solutions-coder/bcordes/issues/35) in [Clean up comments and documentation across bcordes](https://github.com/bc-solutions-coder/bcordes/issues/34). It does not apply the cleanup or settle the documentation design. Source links below point to the audited commit so the evidence survives later file moves.

## Coverage

The audit covers the 478 tracked paths at commit `1f11ee106aedd15f6259a0fc905817682d6ee89f`. [coverage.tsv](coverage.tsv) records each path, its Git blob, disposition, reason, and findings. Reviewers read eligible text files in full and checked comments against their surrounding implementation. Exclusions cover skills and their resources, generated or binary assets, third-party artwork, lock metadata, and an empty directory placeholder. Ignored local files were not reviewed.

Reviewed 363 eligible files: 156 need edits and 207 need no change. The other 115 paths are excluded, each with a reason in the ledger.

`needs-edit` identifies audit findings, not completed edits. `reviewed-no-change` means no editorial change was identified; it does not certify the runtime implementation. New audit artifacts are outside the recorded baseline.

Run the coverage check from the repository root:

```sh
python3 docs/audits/2026-09-documentation/verify-coverage.py
```

The script checks for omitted or duplicate paths, mismatched snapshot blobs, invalid dispositions, and missing findings. It verifies the ledger against the recorded commit, not the correctness of editorial judgments or the state of a future branch. During execution, keep a separate change record and account for files added since this baseline.

## Comment editing standard

Delete completed migration chronology, repeated assertions, decorative section labels, and comments that restate the next command or JSX element. Preserve the reason for an unusual choice and any contract a maintainer cannot infer safely. Length alone is not a deletion rule.

| Current example                                                                            | Proposed edit                                                                                                                            |
| ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Dockerfile: "Copy the rest of the source code into the image" before `COPY . .`            | Delete the comment.                                                                                                                      |
| Root ESLint config explains the re-export across four lines.                               | "Edit shared lint rules in @bcordes/config/eslint." Keep `@ts-check`.                                                                    |
| Auth identity is described as resolved from an OIDC JWT.                                   | "Application identity from the API profile and current session." Retain the distinction between API permissions and session scopes.      |
| CSRF documentation mentions anonymous requests but omits tokenless authenticated sessions. | "Checks x-csrf-token on unsafe methods when the session has a CSRF token." This describes the helper, not the SDK BFF security contract. |
| Test comments say "Radix Select polyfills for jsdom" after the Base UI migration.          | "Browser APIs missing from jsdom."                                                                                                       |
| Package tests contain migration steps, former importer counts, and RED/GREEN history.      | Delete finished task history. Keep brief test-isolation or contract explanations where needed.                                           |
| Repeated Tailwind scanning explanations.                                                   | "Scan linked packages so their utilities are generated." Preserve the actual `@source` directives.                                       |

Do not move filler into docs merely to shorten a source file. Move only useful background, give it one canonical home, and leave a reference where a reader needs it.

## Constraints that affect execution

- Existing architecture tests require retirement wording in the ESLint config and exact README headings, tree formatting, and module placement. Minimally adapt affected existing assertions when the documentation changes. Do not add source-text assertions.
- Tailwind scans source text, including comments. The bundle test deliberately avoids spelling a complete sentinel class in its own source. Preserve that constraint when editing comments or examples.
- Preserve `@ts-check`, JSDoc types, lint suppressions, test-environment directives, client directives, shebangs, and notices. Treat machine-consumed comments as behavior-sensitive.
- Preserve meaningful subprocess and test-environment explanations, including `NODE_PATH` isolation, avoiding recursive test runs, React instance sharing, and jsdom limitations. External browser/library claims need verification if rewritten as guarantees.
- Document the actual distinction between SDK session storage and legacy Valkey key helpers. Do not repeat the old claim that unused key builders define the current production session namespace.
- Do not change authorization, token validation, retry policy, or UI behavior in this pass. Comments about these contracts must be checked against callers, not just the function name.
- Changelog entries are historical release records. Keep them historical. Resume facts require owner evidence; a wording edit must not invent or change career claims. Public page copy and machine-consumed sitemap/manifest data are outside this editorial scope.

## Proposed documentation lookup

This is a candidate for [Design the documentation structure and lookup paths](https://github.com/bc-solutions-coder/bcordes/issues/38), not an approved tree. Start with a short root README and a `docs/README.md` engineering index organized by the reader's task. Prefer a small number of complete pages to empty category directories.

| Reader's task                           | Canonical destination to establish                        | Implementation evidence                                                                   |
| --------------------------------------- | --------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Run the app locally                     | Current local setup guide                                 | Root/app manifests, `.npmrc`, local Compose, SDK configuration                            |
| Add a feature or package                | Architecture and contribution guide                       | Feature/shared/app entry points, package exports, ESLint boundary rules                   |
| Authenticate or authorize a request     | Auth guide                                                | `packages/auth/src/{bff,sdk,middleware,session}.ts`, inquiry server functions, `start.ts` |
| Call Wallow                             | SDK integration guide with a short package README pointer | Wallow client/service adapters, generated operations, failure-message handling            |
| Implement notifications or live updates | Current notifications guide                               | Notification server functions, EventStreamProvider, event request allowlist               |
| Build UI and forms                      | UI implementation section or guide                        | UI/forms exports, theme tokens, both `components.json` files, Storybook                   |
| Verify a change                         | Testing guide linking to browser fixture details          | Vitest projects, e2e README, Playwright configuration, smoke scripts, CI                  |
| Configure and deploy                    | Deployment runbook plus environment reference             | Production Compose, `.env.example`, Dockerfile, release workflows                         |
| Understand terms or prior decisions     | Domain glossary and selected historical rationale         | `CONTEXT.md`, retained decisions, linked issues                                           |

For example, a contributor adding an inquiry action should reach the feature guide from the index, follow its SDK/auth references, find the current inquiry server-function example, and then reach the relevant behavior tests. They should not need to choose between an old scaffold tutorial and the current SDK integration.

Keep `docs/agents` separate from application guidance and leave skills untouched. Do not include the resume in the engineering index. Resolve historical-document dispositions before adding links that might soon disappear.

## Verification for the cleanup

1. Track every `needs-edit` finding through a change or a documented no-change decision. Preserve this baseline; record the executed changes separately and include new files.
2. Check implementation claims against current source, manifests, configuration, and tests. Mark unresolved external facts and reuse the existing Wallow release-verification ticket rather than claiming a local audit proves them.
3. Verify all moved-page references, source pointers, command names, environment variables, and package exports. Check Markdown links and HTML image paths. The audit's simple inline Markdown path scan found no missing targets; it does not validate anchors, HTML, external URLs, or paths shown only in code blocks.
4. Review source diffs for comment-only intent and preserve directives and string literals. Run formatting, lint, and typecheck for affected source, plus affected existing tests. Run the Tailwind bundle test when scanned comments change. Use production build and smoke/browser checks when the affected behavior or documented command requires them.
5. Verify each rewritten setup, build, and test command where the required local services and credentials are available. Record unavailable live checks explicitly. Do not provision or change a production service merely to validate wording.
6. Check the proposed navigation with concrete lookup tasks, then commit intended files, rebase, push, and verify the remote branch. Preserve unrelated work.

This audit ran no application behavior tests and certified no live Wallow endpoints. Its deliverables are the per-file findings, implementation evidence, coverage check, and decisions to take before editing.
