# Shell error recovery and auth validation proposal

Proposal for [Decide coverage for shell error recovery and auth input validation](https://github.com/bc-solutions-coder/bcordes/issues/78). **Awaiting human acceptance; no tests or product behavior have been changed.**

Recommend including both gaps in the required implementation plan. They protect existing supported behavior and complement the accepted review of current cases. They are not optional coverage padding and do not reopen already-accepted dispositions.

## Root error behavior

Current `apps/web/src/routes/__root.tsx:68` registers RouteError as the root error component. It displays 500, Something Went Wrong, explanatory text, Try Again and Go Home. Try Again invokes the router-provided reset callback. Only a development build and an Error instance display the error message. The current root test suite does not exercise this component.

This decision owns new scenarios in `apps/web/src/routes/__root.error.test.tsx`. Exercise the actual registered component and real router; do not export a second implementation solely for tests or copy its JSX. An isolated component assertion may observe its public reset callback, but real-boundary wiring must also be demonstrated.

| Required scenario                                               | Observable evidence                                                                                                                                                                                                                                                        | Relevant defect                                                                 |
| --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Failed route shows a usable generic fallback                    | Trigger a controlled child failure through the real root error boundary; assert named error heading, explanation and both recovery controls. Cover Error and a non-Error thrown value.                                                                                     | Missing registration, missing fallback or crashing on a non-Error value.        |
| Development detail appears only for an Error                    | Run the real component under explicit development mode; a distinctive Error message appears, while a non-Error string/object does not become a rendered diagnostic.                                                                                                        | Wrong type/mode guard or hidden expected development message.                   |
| Production fallback hides diagnostic detail                     | In the production browser scenario below, trigger a distinctive controlled error and assert generic visible fallback without that diagnostic in rendered content.                                                                                                          | Removing the production guard exposes the message.                              |
| Try Again invokes reset and clears a recoverable render failure | Observe the public reset callback for the registered component. Also use a real router with a child that stops throwing after controlled external state changes; clicking Try Again renders its recovered content. If the child still throws, the fallback remains usable. | Disconnected reset button, missing reset wiring or incorrect boundary recovery. |
| Go Home leaves the failed route                                 | Activate the named link with a real router and assert the home destination and its content.                                                                                                                                                                                | Wrong target or unusable navigation from the fallback.                          |

“500” here is displayed content, not proof of an HTTP response status. Try Again resets the boundary; this plan does not require it to refetch a failed loader, retry a network operation, or guarantee that a persistent failure disappears. If such behavior is later desired, it needs an explicit product decision.

This decision owns the production integration scenario in new `apps/web/e2e/tests/shell-error-recovery.spec.ts`. Use the real built app with an isolated controlled backend failure on an existing route, then assert generic fallback and Go Home. Do not create a production error-demo route. Unit scenarios cover reset of a transient render failure; browser coverage proves the production build's visible fallback and navigation. Do not claim secrecy for all serialized server data from a visible-DOM assertion.

Do not preserve exact console calls, source text, component shape, wrapper classes or generated IDs. Scope any expected-error console interception to the test and restore it; never suppress runner diagnostics globally.

## Shared auth input validation

Current `apps/web/src/shared/auth/server-fns/auth.ts:5` registers an object validator with optional string returnTo, then awaits the real middleware. The existing adapter in `auth.test.ts` discards `inputValidator`, so the existing four cases cannot establish validation. Middleware encodes a truthy string into the login return destination; an omitted or empty value uses the plain login URL.

This decision owns new validation scenarios in the existing `apps/web/src/shared/auth/server-fns/auth.test.ts`. The [accepted shell review](https://github.com/bc-solutions-coder/bcordes/issues/62#issuecomment-5572176302) still owns that file's existing handler-outcome rewrites. Combine valid-input rows with those outcomes rather than duplicating them.

| Required scenario                                 | Observable evidence                                                                                                                                                                                                                              | Relevant defect                                                        |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| Malformed outer input fails before auth work      | Pass null, a string and an array into the actual registered validator. Assert a validation failure and no session read or SDK request.                                                                                                           | Bypassing object validation.                                           |
| Non-string returnTo fails before auth work        | Cover null, number, boolean, array and object field values. Assert a validation failure, not just any rejection, and no session/SDK work.                                                                                                        | Loosening the field or invoking the handler before validation.         |
| Valid input survives validation unchanged         | Cover omitted returnTo, explicit undefined in the harness, empty string and a local path with query/fragment. Feed the parsed value into real middleware and reuse the accepted redirect/completion scenarios.                                   | Making the field required/nonempty or dropping/changing its value.     |
| Built transport enforces the configured validator | Use the production scenario below with one malformed numeric returnTo and a valid control. The malformed request fails validation rather than redirecting or succeeding; the valid request still completes the expected authenticated operation. | A no-op transport validator or a transport that rejects every request. |

The validator harness must execute the actual validator supplied to the framework builder, feed its parsed output to the actual handler, and run real middleware with controlled session/SDK boundaries. Do not copy the schema. A malformed input that merely reaches anonymous middleware and throws a login redirect must fail the test. This harness proves configured validation and handler order, not framework request serialization.

Include a separate real-transport scenario in new `apps/web/e2e/tests/auth-input-validation.spec.ts`, owned by this decision. Discover the actual generated request through a legitimate browser interaction and the current framework transport/serializer; do not hard-code function hashes, parse generated source, or call an invented endpoint. Use isolated authenticated fixture observation as planned in the accepted browser review. Replay a valid control, then a malformed numeric return destination and assert validation rejection with no additional auth-backend request. Do not freeze framework error wording/status unless it is a supported public contract; distinguish validation failure from redirect, unrelated routing failure or generic server failure.

The current schema imposes no local-path, nonempty, trimming, maximum-length or strict-unknown-property policy. Do not add those constraints or claim their protection here. In particular, this decision is not certification of redirect-destination safety throughout the authentication system. Existing browser logout/origin checks and package middleware cases retain their owners.

## Ownership and verification

This decision owns only the added scenarios listed above and its two new browser files. Existing shell tests, middleware tests, browser redirect/security tests, inquiry/settings validation and boot loading behavior remain under their accepted owners. [Add boot loading screen](https://github.com/bc-solutions-coder/bcordes/issues/14) remains outside this gap decision. Include all new files in final inventory reconciliation; do not count these requirements as currently implemented tests.

Observed validation: the two existing root/auth suites passed all 12 current cases with none skipped. That run establishes no new gap protection. [summary.json](summary.json) records this evidence and planned ownership. No fresh coverage measurement or production transport probe was performed in this planning decision.

During implementation, demonstrate the listed deliberate defects fail and restored behavior passes. Run affected tests, production build and the new browser scenarios, then full coverage and relevant final gates. The accepted requirement to reach and enforce 90% for lines, statements, branches and functions remains; do not reduce thresholds or expand exclusions. If actual router/transport behavior contradicts a proposed scenario, report it as a concrete finding before changing product behavior or substituting a stub-only claim.
